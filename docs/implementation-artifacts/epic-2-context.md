# Epic 2 Context: Studenter kan melde et problem

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

En besøkende oppretter konto og logger inn med e-post og passord, og en innlogget bruker registrerer en rapport med beskrivelse, lokasjon, kategori og valgfritt bilde. KI-en foreslår kategori og en kort oppsummering før innsending, og rapporten vises etterpå på detaljsiden med status **Ny** og «1 har sett dette». Epicen gjør LocalFix til et verktøy der studenter selv melder problemer (UJ-1), og den lukker det åpne spørsmålet om KI-leverandør med et fast testsett. Alt skal virke uten nøkler: KI-en går i mock-modus, og sensor kan registrere rapporter lokalt.

## Stories

- Story 2.1: Konto og innlogging
- Story 2.2: Registrere en rapport
- Story 2.3: KI-forslag for kategori og oppsummering
- Story 2.4: Legge ved et bilde
- Story 2.5: Velge KI-leverandør med SM-5-testen

## Requirements & Constraints

- **Konto:** Registrering med e-post og passord gir innlogging med en gang, uten e-postbekreftelse. Nye kontoer får rollen `user`, og appen lagrer ingen navn. E-postadressen vises bare for brukeren selv. Uten innlogging kan man bare lese, og en besøkende som prøver å registrere, sendes til innlogging og så tilbake dit hen kom fra.
- **Rapport:** Beskrivelse (maks 1000 tegn), lokasjon (maks 200) og kategori (en av fem) er påkrevd. Tekst med bare mellomrom er tom. Grensene gjelder teksten etter trimming og telles likt i skjemaet, i Server Action og i databasen, også med emoji og æøå: nøyaktig grensen godtas, ett tegn mer avvises alle tre steder. En rapport uten bilde og uten oppsummering lagres.
- **KI-forslag:** Kategorien er alltid en av de fem kodeverdiene, ellers «ingen forslag». Oppsummeringen er ren tekst på maks 300 tegn, også når brukeren skriver den selv. Timeout etter 5 sekunder, feil eller ugyldig svar stopper aldri innsendingen: brukeren velger kategori selv og sender uten oppsummering. Uten nøkkel går KI-en i mock-modus.
- **Bilde:** Valgfritt, JPEG, PNG eller WebP, maks 5 × 1024 × 1024 byte, sjekket i skjemaet, i Server Action og i bucketen. Tom fil og bilder med svært store dimensjoner avvises uten at serveren går tom for minne. Filendelsen kommer fra bildetypen serveren fant i fila, ikke fra filnavnet.
- **Personvern:** Serveren fjerner alle EXIF-data (GPS, enhet, tidspunkt) før lagring, og bildet står riktig vei etterpå. Testes med et testbilde med oppdiktede GPS-koordinater. Rapporttekst og e-postadresser logges aldri, heller ikke når KI-kallet feiler. I mock-modus forlater ingen tekst maskinen.
- **Valg av KI-leverandør:** 20 oppdiktede norske beskrivelser, fire per kategori, med fasit. Vinneren treffer minst 16 av 20, gir gyldig JSON hver gang, svarer på under 5 sekunder og har ikke dansk eller nynorsk i oppsummeringene. Kandidatene er Cloudflare, Groq og Mistral. Først avklares om Cloudflare krever betalingskort, hvor inferensen kjører, og gratisgrensene hos Groq og Mistral. Gemini på gratisnivå er utelukket, og velges Mistral, slås trening på dataene av. Bare testsettet sendes ut. Oppfyller ingen kravene, forblir mock standard.
- **Definisjon av ferdig (hver story):** Som i Epic 1: issue, egen branch, PR med `Closes #N`, Playwright, pgTAP og Vitest grønne, axe uten `serious`/`critical`, kjerneflyttesten utvidet bare med tastatur og uten `skip`/`fixme`, ingen horisontal scrolling på 360 og 320 px, rettigheter håndhevet og testet i databasen, testsammendrag og gjennomgangsfunn i PR-en. Regelendringer føres i planleggingsdokumentet (begge kopier der det finnes to) og `docs/beslutninger/` i samme PR. Siste story følger README på en ny klone.

## Technical Decisions

- **Innlogging:** `lib/supabase/auth.ts` eksporterer `getViewer()` (`{ user, isModerator }`, brukeren fra `auth.getUser()`, rollen fra brukerens egen rad i `profiles`, aldri fra JWT eller metadata) og `requireUser(returnTo)`, som sender til `/auth/login?next=<sti>`. Siden for ny rapport og hver Server Action som krever innlogging, kaller `requireUser` først. `next` godtas bare når `new URL(next, origin).origin === origin`, ellers `/`; Vitest dekker `//x`, `/\x`, `https://x` og `javascript:alert(1)`. Nettleserklienten (`lib/supabase/client`) brukes bare i skjemaene for innlogging, registrering og utlogging, aldri til data. `proxy.ts` sender aldri besøkende til innlogging. Startpakkens sider for glemt passord, nytt passord og `protected` fjernes.
- **Profiler:** Raden opprettes bare av triggeren `handle_new_user` (eneste `security definer`, setter `role = 'user'` hardkodet). Ingen Server Action oppretter eller endrer `profiles`.
- **Skriverettigheter:** `authenticated` får INSERT på `reports` som kolonnegrant for `description, location, category, summary, image_path`, og policyen har `WITH CHECK (author_id = auth.uid())`. `author_id`, `status`, `hidden`, `created_at` og `status_changed_at` kommer fra `DEFAULT` og kan ikke settes av brukeren; `anon` kan ikke sette inn. Lengdereglene ligger i `CHECK` med `char_length`, og `lib/limits.ts` teller med `[...s].length`, så pgTAP og Vitest kan vise at de teller likt.
- **Server Actions:** Svarer `{ ok: true, data }` eller `{ ok: false, error: { code, message } }`. Feilkodene er lukket (`unauthenticated`, `validation_failed`, `upload_failed`, `ai_unavailable`, `unknown` med flere) og oversettes i `lib/errors.ts`; tekst fra Supabase eller databasen vises aldri. Tekstfelt trimmes, og tom tekst lagres som `NULL` (også tomt KI-svar). Handlingene sjekker både `error` og antall rader, og kaller `revalidatePath` for lista og detaljsiden.
- **KI-modulen `lib/ai`:** `suggest(description)` gir `{ category, summary }` eller `null`. Adaptere: mock og OpenAI-kompatibel, valgt med `AI_PROVIDER=mock|openai`, med base-URL, modell og nøkkel fra `lib/env.ts` og variablene i `.env.example` uten verdier. Adapteren ber om JSON (`response_format`) der det støttes og tåler JSON i en kodeblokk. Kategorien valideres eksakt mot kodeverdiene i de genererte typene (`Constants`), så feil store og små bokstaver og norske navn avvises. Høyst 2000 tegn sendes, og hver bruker har høyst ett kall i gang (lås i minnet, én prosess). Kallet gjøres bare fra en Server Action for innloggede; en besøkende får `unauthenticated`. Mock svarer forutsigbart etter nøkkelord (for eksempel «gatelys» → `lighting`) og har et fast testord som gir `null`. Testkommandoen setter `AI_PROVIDER=mock` eksplisitt.
- **SM-5-skriptet:** Ligger i `evals/sm5/` og kaller samme `lib/ai` som appen. Det sier tydelig fra når det kjører mot mock, og viser treff av 20, om svaret var gyldig JSON, svartid og oppsummeringene. Valget og resultatene føres i `docs/beslutninger/`, Deferred-raden i arkitekturen og det åpne spørsmålet i PRD-en oppdateres, og `.env.example` viser variablene for vinneren.
- **Bildeopplasting:** En Server Action validerer fila, fjerner EXIF og laster den opp med brukerens sesjon til den private bucketen `report-images`, med stien `<author_id>/<uuid>.<ext>`, alltid ny uuid og uten `upsert`. Bildet lastes opp først, og stien lagres i `image_path`. Feiler opprettelsen av rapporten etterpå, blir fila liggende uten at noen kan lese den; det finnes ingen DELETE-policy, og oppryddingen er utsatt. `serverActions.bodySizeLimit` settes høyt nok for 5 MB pluss overhead. Storage avviser opplasting utenfor egen mappe (`403`/`42501`) og feil type (`415`). EXIF-regelen føres inn i bildeopplastingsbeslutningen i arkitekturen, og biblioteket i Stack-tabellen.
- **Avhengigheter og miljø:** Eksakte versjoner, aldri `latest`, og ingen ny npm-pakke uten at Stack-tabellen oppdateres. Miljøvariabler leses bare i `lib/env.ts`. `supabase/config.toml` (der `enable_confirmations = false` allerede står) endres bare i en egen commit.

## UX & Interaction Patterns

- **Meny i topplinja:** Besøkende ser «Logg inn», og innloggingssiden lenker til «Registrer konto». Innloggede ser egen e-postadresse og «Logg ut», moderatoren i tillegg merkelappen «Moderator». «Logg ut» viser lista som for en besøkende. Begge auth-sidene tar med `next`.
- **Inngang til skjemaet:** Under 640 px en flytende «+»-knapp, 56 px, nede til høyre, `aria-label="Registrer problem"`, eneste egne skygge. Fra 640 px erstattes den av primærknappen «Registrer problem» i topplinja. Tomtilstanden i lista får knappen «Registrer problem» til samme sted.
- **Skjemaet:** Fokus i beskrivelsesfeltet ved åpning. Synlig `label` på alle felt, 16 px tekst i feltene. Beskrivelsen har telleren «N/1000» (leses ikke opp for hvert tegn) og under feltet «Ikke skriv navn eller andre personopplysninger. Teksten sendes til en KI-tjeneste for å foreslå kategori.» Kategorivalget har de fem kategoriene fra `lib/labels.ts`. Lokasjonen har plassholderen «F.eks. gangveien ved bygg A».
- **«Send inn»:** Deaktivert til beskrivelse, lokasjon og kategori er fylt inn, og mens KI-en jobber, med mindre brukeren har valgt kategori selv. Viser «Sender …» under innsending. Etterpå går brukeren til detaljsiden med toasten «Rapporten er sendt inn».
- **Feil:** Valideringsfeil står under feltet, koblet med `aria-describedby`, og fokus flyttes til første feil. Feiler innsendingen, vises destructive-toasten «Kunne ikke sende inn. Prøv igjen.», og alt brukeren har fylt inn, også bildet, beholdes.
- **KI-tilstander:** Forslaget hentes bare når brukeren går ut av beskrivelsesfeltet, med minst 10 tegn som er endret siden forrige forslag (aldri mens hen skriver). Imens står «Finner kategori …» med spinner, og kategorivalget kan brukes. Et forslag velger kategorien med pillen «Foreslått av KI» (`ai-tag`), og skjermleseren hører «Kategori foreslått: Belysning» via `aria-live="polite"`. Pillen forsvinner når brukeren endrer kategori, og KI-en overskriver aldri et eget valg. Oppsummeringen vises som lesetekst med «Endre». Uten forslag: «Vi fikk ikke et forslag. Velg kategori selv.», og kategorivalget står tomt og påkrevd. Mock ser ut som et vanlig forslag.
- **Bilde:** «Legg til bilde» åpner kamera eller bildebibliotek på mobil. Under knappen står «Unngå ansikter og bilskilt på bildet. JPEG, PNG eller WebP, maks 5 MB.» Forhåndsvisningen har 12 px hjørner og kan fjernes. Feil fil avvises med en gang med melding ved feltet.
- **Tilgjengelighet og tester:** axe skanner innlogging, registrering og skjemaet tomt, med valideringsfeil, med KI-forslag og med valgt bilde. Kjerneflyttesten logger inn, bruker mock-forslaget, legger ved et bilde (filvalget er unntatt fra kravet om bare tastatur) og registrerer en rapport bare med tastatur, uten horisontal scrolling på 360 px.
- Tone: du-form, kort og saklig, ingen utropstegn eller emoji.

## Cross-Story Dependencies

- **Fra Epic 1 (ferdig):** Lista, detaljsiden, visningen `reports_with_counts` og bildereglene (AD-6 og AD-9 er `[ADOPTED]` etter spiken, reserven trengs ikke). Bildet vises med én serverfunksjon for signert lenke i `lib/supabase/images.ts`, og bildeikonet i lista finnes, så Story 2.4 bare laster opp. Kontrollen av retur-adressen finnes som `safeNextPath` i `lib/safe-next.ts` og bør gjenbrukes for `next`.
- **Rekkefølge:** 2.1 gir `getViewer`, `requireUser` og menyen som 2.2 trenger. 2.2 gir skjemaet, Server Action og INSERT-reglene som 2.3 og 2.4 bygger på. 2.3 gir `lib/ai`, som 2.5 bruker.
- **Hvis tiden blir knapp:** Story 2.5 forenkles først (én leverandør, eller mock beholdes). Deretter kan «Registrer problem» i topplinja droppes, og den flytende knappen beholdes på alle bredder (2.2), men det krever at `EXPERIENCE.md` (begge kopier) og beslutningsloggen oppdateres.
- **Utsatt arbeid som blir aktuelt:** «←» på detaljsiden går tilbake i historikken uansett forrige side, og bør gå til lista når forrige side er skjemaet eller innloggingen (Story 2.2). En norsk `app/not-found.tsx` mangler for ukjente URL-er.
- **Senere epics:** Epic 3 bruker `requireUser` for bekreftknappen (besøkende sendes til innlogging og tilbake) og `authored_by_me` for «Mine rapporter». Moderatorrollen fra `getViewer` brukes i Epic 4.
