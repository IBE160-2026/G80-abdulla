## (c) RLS on storage.objects with subquery, and security_invoker views

### c1. Policy on `storage.objects` that looks up `public.reports`

Status: confirmed in practice, not confirmed by an official Supabase page.
- The official Storage access-control page (https://supabase.com/docs/guides/storage/security/access-control, fetched 2026-10-28) only shows `storage.foldername(name)` and `auth.jwt()` checks; it does not show or forbid a subquery against another table, and does not mention `createSignedUrl`.
- The general RLS page (https://supabase.com/docs/guides/database/postgres/row-level-security, fetched 2026-10-28) shows policies with `exists (select ... from other_table)` on ordinary tables, and warns about infinite recursion when two tables' policies reference each other.
- Community evidence of the exact pattern on `storage.objects`: https://github.com/orgs/supabase/discussions/31073 (`EXISTS (SELECT 1 FROM products WHERE products.id::text = (storage.foldername(name))[1])`), with the gotcha that an unqualified `name` resolves to the subquery table's column; use `storage.objects.name`. Secondary blog sources only; no official statement.

Implications for AD-6 and AD-9:
- Policies are plain Postgres RLS, so a subquery is technically allowed. The subquery runs as the caller and is itself filtered by `reports` RLS. That actually gives AD-6 for free: `exists (select 1 from public.reports r where r.image_path = storage.objects.name)` returns a row only if the caller can read the report (hidden = false or moderator). Spine should say this explicitly instead of "bruker samme regel".
- Because AD-9 uploads the image before the report exists, the author's SELECT on that object will fail until the report row exists and is visible. Fine for upload (INSERT policy with `bucket_id` and folder = `auth.uid()`), but the "slett bildet hvis opprettelsen feiler" step needs a DELETE policy that does not depend on `reports` (owner or folder = `auth.uid()`), and a signed URL for the author's own just-created image only works once the report exists. The spine does not specify the DELETE policy.
- Hidden report plus author: the author of a hidden report cannot read their own report under the stated rule (hidden = false or moderator), so they would lose their own image link. Check whether FR-9 intends that; if not, add `author_id = auth.uid()` to the read rule in AD-6.
- Index `reports.image_path` (unique), since the policy runs per object.
- createSignedUrl privilege: not confirmed in docs fetched. Standard behavior (community and Supabase storage source) is that creating a signed URL requires SELECT on `storage.objects` for the caller. Unverified here; keep in Deferred, but narrow it: "createSignedUrl krever antatt SELECT-policy; test med pgTAP mot `storage.objects`".

Proposed fix: shorten the Deferred row to the two truly unverified bits (createSignedUrl privilege, and the DELETE/author-read behavior above), and add one sentence to AD-6: "Policyen bruker `exists (select 1 from public.reports ...)` kvalifisert med `storage.objects.name`; underspørringen filtreres av reports sin egen RLS."

### c2. `security_invoker` views and local Postgres version

Status: confirmed.
- Supabase RLS docs: "Views bypass RLS by default because they are usually created with the `postgres` user"; for Postgres 15+ use `with (security_invoker = true)`. Source: https://supabase.com/docs/guides/database/postgres/row-level-security, 2026-10-28.
- Local Postgres: the CLI config template (`apps/cli-go/pkg/config/templates/config.toml` in supabase/cli, read 2026-10-28) sets `[db] major_version = 17`; the template Dockerfile pins `supabase/postgres:17.11.0.008` and also `15.19.0.008`. The config docs (https://supabase.com/docs/guides/local-development/cli/config) say the default is 15 and must match the remote; the template in the current repo says 17. Either way both are 15+, so `security_invoker` works locally.

Design gap to add to AD-5/AD-7: the count view runs as the caller, so `confirmations` SELECT policy must let any user see all confirmations of reports they can read (not just their own), or the counts will be wrong for everyone. The spine states no SELECT policy for `confirmations`. Add: "SELECT på confirmations er tillatt når rapporten er synlig for brukeren".

## (d) Local bucket config in `config.toml`

Status: confirmed.
- Keys: `[storage.buckets.<name>]` with `public`, `file_size_limit` (e.g. "5MB"), `allowed_mime_types` (list), `objects_path` (local directory uploaded to the bucket). Sources: https://supabase.com/docs/guides/local-development/cli/config and the CLI template (commented example: `public = false`, `file_size_limit = "50MiB"`, `allowed_mime_types = ["image/png","image/jpeg"]`, `objects_path = "./images"`), 2026-10-28. Global `[storage] file_size_limit` default is "50MiB".
- Seeding files: `supabase seed buckets` reads `<workdir>/supabase/<objects_path>/**` recursively; a relative `objects_path` resolves under `supabase/`; `db reset` seeds buckets after SQL seed (SIDE_EFFECTS.md in supabase/cli `apps/cli/src/commands/seed/buckets` and `db/reset`), 2026-10-28. If storage is not ready, db reset only prints a warning and skips, so it may fail silently.
- The bucket itself is created from config, so the migration does not need `insert into storage.buckets` locally (but for a non-local environment it would).

This resolves the Deferred row "Hvordan testbilder havner i Storage ved seed" for the local case.

Proposed fix: 
- Replace that Deferred row with a decision in AD-11 or AD-9: `[storage.buckets.report-images] public = false; file_size_limit = "5MiB"; allowed_mime_types = ["image/jpeg","image/png","image/webp"]; objects_path = "./seed-images"`.
- Rename/layout constraint: because `image_path` is `<author_id>/<uuid>.<ext>`, the files under `supabase/seed-images/` must be laid out as `<seed-user-uuid>/<name>.jpg` so that `seed.sql` `reports.image_path` values match. State that seed user UUIDs are fixed in `seed.sql`.
- Add to README: after `supabase db reset`, check that buckets were seeded (warning is non-fatal); fallback command `supabase seed buckets`.
- Unverified: whether 5MB in the bucket config means 5 * 1000 * 1000 or 5 MiB; spine says 5 MB in app, so set the bucket limit slightly higher than the app limit (e.g. "6MiB") to avoid disagreement.

## (e) `supabase test db` / pgTAP for RLS

Status: confirmed.
- CLI doc (apps/cli/docs/supabase/test/db.md in supabase/cli, 2026-10-28): "Executes pgTAP tests against the local database", requires `supabase start`, runs `pg_prove` in a container with tests mounted from `supabase/tests`, files `.sql` or `.pg`, each test in its own rolled-back transaction.
- `supabase test new <name>` writes `supabase/tests/<name>_test.sql`.
- Official RLS testing example (https://supabase.com/docs/guides/local-development/testing/overview, 2026-10-28): impersonate with `set role authenticated` and JWT claims, assert with `results_eq`, `lives_ok`, `results_ne`, `finish()`. The docs page does not itself say the directory and does not mention `supabase_test_helpers` (a separate community extension; do not assume it is installed).

Spine matches (`supabase/tests/`). Fix: add that tests need `supabase start` running, so Docker is required for CI/tests too, and that impersonation of users is done with `set local role authenticated` plus `request.jwt.claims`, not with the service role. Also add pgTAP tests for storage policies (the Deferred verification can be done as a pgTAP test).

## (f) Zod 4.x, Vitest 5.x, Next.js 16

Status: confirmed with caveats.
- Zod 4.6.7 exists (npm). It is framework-neutral TypeScript. No peer dependency on Next. Compatibility with Next 16 is not stated anywhere but there is no mechanism for conflict. Unverified in the sense of "no source says so".
- Vitest 5.0.5 exists (npm). Requires Node `^22.12 || ^24 || >=26`, peer `vite ^6.4 || ^7 || ^8`. Node 24.19.0 is OK. Next.js 16.4.3 requires Node >=20.9 and React `^18.2 || ^19`, so both are fine on Node 24.
- Next.js docs, Vitest guide (https://nextjs.org/docs/app/guides/testing/vitest, lastUpdated 2026-08-25): Vitest does not support async Server Components; unit-test only sync components and logic. The spine already limits Vitest to pure logic (AI adapter, validation), which is consistent. The guide's install list shows `vitest @vitejs/plugin-react jsdom @testing-library/react vite-tsconfig-paths`; the doc does not say which Vitest major it was tested against. Vitest 5 + that guide is unverified; Vitest 5 is only 2 patch releases old, so expect some friction. If the team hits problems, pinning to the latest 4.x is the fallback.
- Server Actions body limit: Next docs (https://nextjs.org/docs/app/api-reference/config/next-config-js/serverActions, lastUpdated 2026-08-26): default `bodySizeLimit` is 1MB, set via `experimental.serverActions.bodySizeLimit`; limit applies to the raw multipart body and the docs recommend 10-20 KB of headroom. This supports AD-9 ("høyt nok for 5 MB pluss overhead"), but the spine should give the concrete value (for example `'6mb'`) and note the key sits under `experimental` in the docs.

Proposed fix: Stack table note "Vitest 5 er ny; bruk 4.x hvis oppsett mot Next feiler". Add `@vitejs/plugin-react`, `jsdom`, `vite-tsconfig-paths` as expected dev deps, or state that no component tests are written (only `node` environment for pure logic, then none of these is needed).

## (g) Other findings the spine does not state

1. **Browser Supabase client in the starter vs AD-3 / dependency rule.** The starter's `components/login-form.tsx`, `sign-up-form.tsx` and `logout-button.tsx` are `"use client"` and import `@/lib/supabase/client` (`createBrowserClient`) to call `signInWithPassword` / `signOut`. AD-3 says the browser never calls Supabase and the layer table says `components/` never imports `lib/supabase/`. Following AD-2 literally violates AD-3. Fix: add to AD-2/AD-3 that the starter's auth forms must be rewritten to Server Actions and `lib/supabase/client.ts` removed (or explicitly allow a browser client for Auth only, and state that data calls still go via the server). Auth calls from the browser are not "data", so the second option is also defensible, but the spine must choose.
2. **Starter includes demo content** (`tutorial/`, `hero.tsx`, `deploy-button.tsx`, `theme-switcher.tsx`, `next-themes`). Add a first-build task to strip these; theme switcher interacts with DESIGN.md.
3. **`middleware.ts` vs `proxy.ts`.** Next 16 renamed it; the spine does not use either name. Mention `proxy.ts` since session refresh depends on it.
4. **`getClaims()`**: the starter uses `supabase.auth.getClaims()` for session checks in the proxy; AD-1/AD-7 and Server Actions should use `getUser()` or `getClaims()` consistently. Not researched in depth; unverified which the team should use in Server Actions.
5. **Docker Desktop**: marked "ikke installert ennå". pgTAP, `supabase start`, and the bucket seeding all depend on it. Nothing here could be run to verify behavior end to end; all CLI behavior above comes from repo docs and source, not from execution. Treat the first `supabase start && supabase db reset && supabase test db` as the real verification.
6. **Local Postgres major version** differs between docs (default 15) and CLI template (17). Pin `major_version` explicitly in `config.toml` and note it in the spine.
